# Plano: Dream nightly com auto-edit seguro na sua própria infraestrutura

## Filosofia

O P7 protege **conteúdo de metodologia** (AGENTS.md, PROJECT_STATE.md, progress.json, dependency_graph.yaml, domains/**), mas **não protege as próprias ferramentas do Dream**. A partir de agora o Dream pode evoluir-se a si próprio desde que:

1. Só toca em `scripts/dream/*`, `.zcode/hooks/*`, `dream/LESSONS.md`, `dream/MEMORY_PATCHES/*`, `dream/STATE/*`, mais criação de novos `dream/*.md`
2. Cada auto-edit passa por uma validação syntax-check + dry-run antes do commit
3. Cada commit tem prefixo `[DREAM SELF-TUNE]` com rationale explícito
4. Self-edits ao kg-reminder.sh são validados com um smoke-test (input simulado + check de append ao hook.log)

## Prompt do Dream — versão revista

O prompt actual mantém-se **estruturalmente igual**. Só estas 3 secções mudam:

### P7 (re-escrito para clarificar scope)
```
P7 (NON-NEGOTIABLE) — protects methodology content, NOT dream infrastructure:

NEVER edit (propose-only, P7-protected):
  - AGENTS.md, 00_METHODOLOGY/AGENTS.md
  - 02_CASES/*/PROJECT_STATE.md, 02_CASES/GLOBAL_PROJECT_STATE.md
  - 02_CASES/*/progress.json
  - 00_METHODOLOGY/dependency_graph.yaml
  - 00_METHODOLOGY/PREPROCESSING_by_domain/domains/**  (also guard-blocked)
  - any other methodology/state file

MAY auto-edit (with logged rationale + commit prefix `[DREAM SELF-TUNE]`):
  - scripts/dream/*.py, scripts/dream/*.sh
  - .zcode/hooks/*.sh
  - dream/LESSONS.md, dream/MEMORY_PATCHES/*.md, dream/STATE/*
  - new dream/*.md files (e.g. dream/SELF_TUNE_LOG.md, dream/STALE_PROPOSALS.md)

Pre-commit validation (mandatory for any auto-edit):
  1. python3 -m py_compile <file>  (Python)
  2. bash -n <file>  (Bash)
  3. --help / dry-run / stdin smoke (must succeed)
  4. git diff --stat  (must show change in scope only)
```

### Passo 7 (novo) — Self-tune pass
```
7. SELF-TUNE PASS (LLM-assisted; new): review this run's LESSONS + net-new
   amendments + drift patterns. If a clearly mechanical improvement emerges
   (e.g. amendment disappeared due to a parser blindspot, drift count
   unchanged across N consecutive cycles, heuristic gate needs adjustment),
   edit scripts/dream/*.py or dream/LESSONS.md following the rules above.
   Append a one-line entry to dream/SELF_TUNE_LOG.md describing what changed
   and why. Commit prefix: `[DREAM SELF-TUNE] <scope>: <action>`.
```

### Passo 8 (novo) — Stale-proposal archiving
```
8. STALE-PROPOSAL ARCHIVE (new): if a proposal title appears in 5+
   consecutive nightly reports without resolution, move it to
   dream/STALE_PROPOSALS.md with first_seen/last_seen dates and a
   `[AWAITING-HUMAN-VERDICT]` tag. This breaks the stagnation loop without
   losing signal.
```

## Implementação faseada

### Fase 1 — Infraestrutura de self-tune (commit único)
1. Criar `dream/SELF_TUNE_LOG.md` (vazio, com header explicativo)
2. Criar `dream/STALE_PROPOSALS.md` (vazio, com header explicativo)
3. Editar o prompt do Dream (no orquestrador — fora do repo) para incluir P7 re-escrito + passos 7-8
4. Adicionar helper `scripts/dream/self_tune.py` com:
   - `validate_python(file)` → `python3 -m py_compile`
   - `validate_bash(file)` → `bash -n`
   - `validate_hook_smoke(file)` → stdin simulado + check de append
   - `git_diff_scope(file)` → fail se mudança fora do scope permitido
   - `commit_self_tune(message, files)` → git add + commit com prefix
5. Testar com um dry-run que falha (simular edição inválida) → confirmar rollback

**Validação final**: `bash scripts/dream/self_tune.py --self-test` deve passar

### Fase 2 — First self-tune execution (cron-driven)
A próxima execução do Dream nightly (quarta-feira 23:55) deve:
- Detectar que amendments #2 e #3 já estão estáveis há 6+ noites → arquivar como stale
- Detectar que drift count = 2 é idêntico ao da noite anterior → adicionar escalation marker ao RECONCILIATION.md ("2nd consecutive cycle, same files — HUMAN ACTION PENDING")
- Commitar 2 self-tunes separados

### Fase 3 — Estabilização (semanas 2-3)
Monitorizar `dream/SELF_TUNE_LOG.md` por regressões. Se algum self-tune causar um WEAK/FAIL no `harness_audit.py`, o próximo Dream reverte (rollback via git revert do commit SELF-TUNE).

## Riscos e mitigações

| Risco | Mitigação |
|---|---|
| Dream introduce bug em adoption_audit.py | py_compile + --help + dry-run antes do commit; próximo nightly detecta |
| Dream entra em loop (edita → reverte → edita) | SELF_TUNE_LOG.md previne edits duplicadas; `dream/STALE_PROPOSALS.md` quebra o loop de amendments |
| Dream tenta tocar em AGENTS.md "para se ajudar" | guard-protected-files.sh já bloqueia; reforçar com check explícito no self_tune.py |
| Smoke-test do hook é flaky | kg-reminder.sh já é determinístico; o helper limpa o sentinel antes de testar |
| P7-protected files editados por engano | self_tune.py verifica path contra blocklist explícita antes de qualquer edit |

1. `bash scripts/dream/self_tune.py --self-test` → exit 0
2. Próxima execução Dream nightly (cron 23:55) deve produzir 2 commits SELF-TUNE se houver signal
3. `harness_audit.py` continua a report HEALTHY para `script:adoption_audit.py`, `script:reconcile.py`, `script:brief.sh`
4. `git log --grep SELF-TUNE` mostra apenas commits com scope restrito a `scripts/dream/*` e `dream/`
5. Working tree permanece limpo entre dream nightly runs (self-tunes são determinísticos)
